# 音效设计文档

`designs/` 记录 Mod 应当呈现的听觉行为，以及经人工评审后可交给
builder 实现的技术契约。它与其它资料的职责不同：

- `docs/mapping/` 记录原版 Bank、WEM、事件和动作的逆向结果。
- `docs/` 下的其它研究文档记录资料来源、实验过程和实机观察。
- `designs/` 记录要保留、替换或叠加哪些声音，以及必须满足的正负触发范围。
- `builders/` 是最终可执行实现。构建过程不得在运行时解析 design 文档。

## 元数据

每份设计使用以下 YAML front matter：

```yaml
---
design_id: wp07.example-design
status: draft
target_artifacts:
  - sound/wwise/Windows/example.nbnk
---
```

- `design_id`：稳定、唯一的设计标识；批准后不因标题或文件名调整而变化。
- `status`：只能是 `draft`、`approved` 或 `retired`。
  - `draft` 表示仍有素材、路由或实机验收项未获人工批准，不可据此自动落地 builder。
  - `approved` 表示设计目标、正式素材、guard 和验收范围均已完成评审。
  - `retired` 表示设计不再参与后续实现，但保留作历史记录。
- `target_artifacts`：受设计影响的 `nativePC` 相对输出路径，不是本地原始样本路径。

设计文档不是配置格式。YAML 仅提供稳定身份和评审状态；正文中的判断、约束和待办需要由
实现者完整阅读，不能只抽取表格后直接生成代码。

## 正文模板

```markdown
# 设计名称

## 设计目标

说明玩家应听到什么、原音是否保留，以及为什么这样设计。

## 触发范围

分别列出必须触发和不得触发的动作、状态与重复播放规则。

## 声音层

列出正式处理音频、播放阶段、替换／叠加方式、空间定位和共享关系。

## 技术实现契约

记录受影响 artifact、1-based DIDX 与预期 Media ID、Event/Action/Sound 路由、guard、
允许变化的结构和必须保持不变的结构。复杂研究过程只链接证据，不在这里重复。

## 验收

分开记录静态结构检查和可恢复实机环境中的正向、负向、音量、声道、位置感及抢占测试。

## 证据与待办

链接 mapping、动作资料、研究记录和正式处理音频，并明确所有阻止设计进入 `approved`
状态的未决事项。
```

## 维护规则

- 一个文档对应一个用户可感知的动作或一组不可分割的多阶段声音，不按 WEM 行机械拆分。
- `docs/mapping/` 中的 `Audio` 列在 builder 解耦完成前仍是历史构建输入，但不能替代设计审批。
- 不得把测试探针、占位音频或仅凭动作长度推断的路由写成已批准方案。
- 设计与当前 builder 不一致时，先报告差异；不得为了让测试通过而静默改写设计目标。
- 静态解析成功不能替代实机触发、音量、声道、空间感和 Mod 冲突测试。
